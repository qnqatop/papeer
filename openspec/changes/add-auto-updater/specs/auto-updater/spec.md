## Назначение

Встроенная в приложение проверка новых релизов, загрузка пакета обновления под текущую платформу и самозамена запущенного бинарника с перезапуском — всё запускается пользователем из раздела «Настройки → О программе».

## ADDED Requirements

### Requirement: Пользователь может проверить наличие обновлений

Система ДОЛЖНА (SHALL) запрашивать GitHub Releases API, получать последний тег версии, сравнивать его с текущей (вшитой при сборке через `-ldflags`) по правилам семантического версионирования и сообщать результат.

#### Scenario: Обновление доступно

- **КОГДА** пользователь нажимает «Проверить обновления» и GitHub API возвращает тег с версией выше текущей
- **ТОГДА** система показывает номер новой версии рядом с текущей и кнопку «Скачать обновление»

#### Scenario: Уже последняя версия

- **КОГДА** пользователь нажимает «Проверить обновления» и текущая версия равна или выше последнего релизного тега
- **ТОГДА** система показывает сообщение «У вас последняя версия» с номером текущей версии

#### Scenario: Сетевая ошибка при проверке

- **КОГДА** система не может достучаться до GitHub API (таймаут, DNS, HTTP-ошибка)
- **ТОГДА** система показывает локализованное сообщение «Не удалось проверить обновления» с причиной; приложение продолжает работать в штатном режиме

#### Scenario: Исчерпан лимит GitHub API

- **КОГДА** GitHub API возвращает HTTP 403 с заголовками rate-limit
- **ТОГДА** система сообщает, что проверка временно недоступна, и предлагает повторить позже

### Requirement: Пользователь может скачать обновление

Система ДОЛЖНА (SHALL) загружать подходящий под текущую платформу ассет из последнего GitHub-релиза, сообщать о прогрессе в реальном времени и проверять целостность архива перед распаковкой. Система ДОЛЖНА распаковывать архив во временную директорию за пределами пути запущенного приложения.

#### Scenario: Успешная загрузка

- **КОГДА** пользователь запускает скачивание
- **ТОГДА** система стримит ассет во временный файл, сообщает прогресс в процентах и байтах, и после завершения распаковывает архив в стейджинг-директорию

#### Scenario: Ассет для платформы не найден

- **КОГДА** в последнем релизе нет ассета, соответствующего текущей платформе (darwin, windows, linux)
- **ТОГДА** система показывает локализованную ошибку «Обновление не поддерживается на этой платформе» и прерывает загрузку

#### Scenario: Ошибка записи при загрузке

- **КОГДА** запись скачиваемого архива во временную директорию не удаётся (нет места на диске, нет прав)
- **ТОГДА** система удаляет неполный временный файл, сообщает об ошибке и не переходит к распаковке

#### Scenario: Повреждённый архив

- **КОГДА** скачанный архив не распаковывается (битый zip/tar.gz)
- **ТОГДА** система удаляет неполную загрузку, сообщает об ошибке и не переходит к установке

#### Scenario: Обрыв загрузки

- **КОГДА** сеть обрывается в середине скачивания
- **ТОГДА** система сообщает об ошибке и возвращается в состояние «Обновление доступно», чтобы пользователь мог повторить

### Requirement: Пользователь может установить обновление и перезапуститься

Система ДОЛЖНА (SHALL) заменить запущенный бинарник/бандл на скачанный и перезапустить приложение. На macOS — замена `.app`-бандла на месте (ядро ОС удерживает inode'ы запущенного бинарника). На Windows — создание временного PowerShell-скрипта, который ждёт завершения процесса, подменяет `.exe` и запускает заново. На Linux — прямая замена бинарного файла и перезапуск через подмену процесса.

#### Scenario: Успешная установка и перезапуск (macOS)

- **КОГДА** пользователь нажимает «Перезапустить для обновления» на macOS
- **ТОГДА** текущий `.app`-бандл отодвигается в соседнюю резервную копию, новый `.app`-бандл копируется на его место, целостность проверяется, резервная копия удаляется, и новый процесс запускается до завершения текущего

#### Scenario: Успешная установка и перезапуск (Windows)

- **КОГДА** пользователь нажимает «Перезапустить для обновления» на Windows
- **ТОГДА** создаётся и запускается временный PowerShell-скрипт, текущий процесс завершается, скрипт ждёт освобождения `.exe`, заменяет его новым, запускает новый процесс и самоудаляется

#### Scenario: Успешная установка и перезапуск (Linux)

- **КОГДА** пользователь нажимает «Перезапустить для обновления» на Linux
- **ТОГДА** текущий бинарник перезаписывается новым, и образ процесса подменяется через `syscall.Exec` с теми же аргументами — перезапуск прозрачен для пользователя

#### Scenario: Недостаточно прав при установке

- **КОГДА** системе не хватает прав на запись для замены бинарника/бандла
- **ТОГДА** система выдаёт локализованную ошибку с предложением проверить права доступа и повторить

#### Scenario: Проверка целостности после установки

- **КОГДА** новый бинарник/бандл помещён на место
- **ТОГДА** система проверяет, что файл существует и имеет ненулевой размер, перед инициацией перезапуска; если проверка не пройдена — установка отменяется, оригинальное приложение не затрагивается

### Requirement: UI обновлений в настройках

Раздел «Настройки → О программе» ДОЛЖЕН (SHALL) содержать панель «Обновления» с: кнопкой «Проверить обновления», меткой текущей версии, областью статуса последней проверки, прогресс-баром загрузки (видимым во время скачивания) и кнопкой «Перезапустить для обновления» (видимой после успешной загрузки).

#### Scenario: Панель в исходном состоянии

- **КОГДА** проверка ещё не выполнялась в текущей сессии
- **ТОГДА** панель показывает текущую версию и кнопку «Проверить обновления»

#### Scenario: Панель во время загрузки

- **КОГДА** идёт скачивание обновления
- **ТОГДА** панель показывает линейный прогресс-бар с процентами и объёмом переданных данных; кнопки заблокированы для предотвращения повторных действий

#### Scenario: Панель с готовым обновлением

- **КОГДА** загрузка успешно завершена
- **ТОГДА** панель показывает номер новой версии и кнопку «Перезапустить для обновления»; кнопка «Проверить обновления» остаётся доступной для повторной проверки

### Requirement: Пассивная проверка обновлений при запуске

Приложение ДОЛЖНО (SHALL) при запуске в фоне проверять наличие более новой версии и, если доступно значимое обновление (смена major или minor), показывать ненавязчивый баннер. Проверка ДОЛЖНА управляться настройкой (включена по умолчанию), не блокировать запуск и не выполнять загрузку/установку без явного действия пользователя.

#### Scenario: Доступна новая major/minor версия

- **КОГДА** при запуске автопроверка включена и GitHub API отдаёт версию с более высоким major или minor, которую пользователь не скрывал
- **ТОГДА** сверху показывается закрываемый баннер с номером версии и кнопкой «Обновить», ведущей в панель обновлений

#### Scenario: Доступен только patch

- **КОГДА** доступная версия отличается лишь patch-компонентом
- **ТОГДА** баннер НЕ показывается; обновление остаётся доступным вручную в панели «Обновления»

#### Scenario: Пользователь скрыл баннер

- **КОГДА** пользователь закрывает баннер крестиком
- **ТОГДА** система запоминает эту версию и не показывает баннер для неё повторно, в том числе после перезапуска

#### Scenario: Автопроверка отключена

- **КОГДА** тумблер «Проверять обновления при запуске» выключен
- **ТОГДА** фоновая проверка при запуске не выполняется; ручная проверка в панели по-прежнему работает

#### Scenario: Ошибка фоновой проверки

- **КОГДА** фоновая проверка не удаётся (сеть, лимит API)
- **ТОГДА** баннер не показывается и приложение продолжает работать в штатном режиме без каких-либо сообщений об ошибке
