## Контекст

Papeer — десктопное приложение на Wails v2 (Go-бэкенд + Vue 3-фронтенд в нативном WebView). Релизы собираются через GitHub Actions и публикуются как GitHub Releases с платформенными ассетами (`.zip` для macOS `.app`, `.zip` для Windows `.exe`, `.tar.gz` для Linux-бинарника). Версия вшивается при сборке флагом `-ldflags -X ...Version=<тег>`. Инфраструктуры обновлений нет.

## Цели / Не-цели

**Цели:**
- Полный цикл в один клик: проверка → загрузка → установка → перезапуск
- Работа на всех трёх платформах (macOS, Windows, Linux)
- Корректная обработка всех видов ошибок (сеть, диск, права доступа)
- Прогресс загрузки в реальном времени в UI
- Без новых внешних зависимостей — только стандартная библиотека Go

**Не-цели:**
- Автоматическая фоновая **загрузка/установка** без участия пользователя (проверка — да, но действие всегда за пользователем)
- Периодическая проверка по таймеру (только при запуске)
- Дельта-обновления (всегда полный архив)
- Откат на предыдущую версию
- Сохранение кодовой подписи macOS после самозамены
- Бесшумное/фоновое обновление без участия пользователя

## Решения

### Решение 1: Новый пакет `internal/updater/`

Вся логика обновлений инкапсулируется в одном пакете. Структура `app.App` содержит поле `*updater.Updater`, а три экспортируемых Wails-метода (`CheckForUpdates`, `DownloadUpdate`, `InstallAndRestart`) — тонкие обёртки, делегирующие в него.

**Отклонённые альтернативы:**
- Инлайн-логика в `app.go` — грязно, сложно тестировать, смешивает зоны ответственности
- Несколько пакетов — избыточно для одной фичи

### Решение 2: GitHub Releases API для обнаружения версий

Запрос к `https://api.github.com/repos/qnqatop/papeer/releases/latest` (публичный, без авторизации). Парсинг поля `tag_name`, сравнение через `golang.org/x/mod/semver` (уже в `go.mod`). Выбор ассета по шаблону имени: `papeer-{macos|windows|linux}-*.{zip|tar.gz}` (`platformKey()` мапит `darwin` → `macos`, совпадая с именами артефактов из `release.yml`).

**Отклонённые альтернативы:**
- Собственный JSON-манифест на сервере — лишняя инфраструктурная нагрузка, без преимуществ перед GitHub API
- Sparkle appcast (только macOS) — отличное решение для Mac, но не помогает на Windows/Linux; добавляет сложность поддержки отдельного фида

### Решение 3: Платформозависимые стратегии установки

Каждая ОС требует принципиально разного подхода к замене бинарника:

| Платформа | Стратегия |
|---|---|
| **macOS** | Отодвинуть старый `Papeer.app` в соседний бэкап `<app>.old-<pid>` (тот же том → `os.Rename` атомарен, без коллизий имён в `~/.Trash` и без `EXDEV` на внешних дисках), **скопировать** новый бандл на исходное место (`copyDir`, а не `os.Rename` — стейджинг и целевая папка могут быть на разных ФС), проверить целостность установленного бинарника (при провале — откат из бэкапа), удалить бэкап, `chmod +x` бинарник, перезапустить через LaunchServices (`open -n <installed.app>` — даёт GUI-сессию и Dock; фоллбэк — прямой `exec.Command`, при полном провале возврат ошибки без `os.Exit`) |
| **Windows** | Создать временный `update.ps1` в `%TEMP%`. Скрипт: ждёт 3с, копирует `papeer.exe` из стейджинга в папку установки, запускает, самоудаляется. Пути подставляются как одинарно-кавычечные PS-литералы с экранированием. Основной процесс: `os.StartProcess("powershell", ...)` и `os.Exit(0)` |
| **Linux** | Скопировать новый бинарник во временный файл **рядом с целевым** (`<exe>.new`, та же ФС), затем `os.Rename` поверх старого (атомарно), проверить целостность, `syscall.Exec` с теми же `os.Args`. Прямой `os.Rename` из `os.TempDir()` невозможен: `/tmp` часто отдельный монтпоинт (`tmpfs`) → `EXDEV` |

**Отклонённые альтернативы:**
- Универсальный подход с `os.Rename` — не работает на Windows (блокировка файла) и macOS (`.app` — директория, не файл)
- Внешняя утилита-апдейтер — усложняет сборку, требует дистрибуции второго бинарника и интеграции в CI

### Решение 3a: Сохранение прав и симлинков при распаковке

Распаковка (`extractZipFile`/`extractTarGz`) сохраняет режим файлов из архива (`os.OpenFile` с mode из entry, а не `os.Create` с `0666`), иначе исполняемый бит теряется и относейнутое приложение не запускается. Симлинки воссоздаются как симлинки (в macOS `.app` фреймворки их используют). На всякий случай перед запуском бинарник дополнительно `chmod +x`.

### Решение 4: Стейджинг во временной директории ОС

Архив скачивается в `os.TempDir()` и распаковывается в поддиректорию `papeer-update/`. После успешной установки — удаляется. При ошибке — остаётся для диагностики. Это позволяет избежать cross-device перемещений и проблем с правами в директории приложения.

### Решение 5: Прогресс через Wails EventsEmit

Цикл загрузки шлёт события `update:download-progress` (проценты, скачано байт, всего байт) через `runtime.EventsEmit`. Фронтенд слушает их через Wails `EventsOn`. Это исключает поллинг и сохраняет отзывчивость UI.

### Решение 6: Без авторизации для GitHub API

Запросы неаутентифицированные. Лимит — 60 запросов/час с одного IP, чего более чем достаточно для ручной проверки обновлений. Никакой возни с токенами для пользователя.

**Отклонённая альтернатива:** требовать GitHub PAT — лишнее трение, избыточно для чтения публичных метаданных релиза.

### Решение 7: Пассивная проверка при запуске (major/minor)

При старте `Startup` в фоне запускает `checkForUpdatesPassive()` (после короткой задержки, чтобы фронтенд успел подписаться). Если автопроверка включена (`auto_update_check != "false"`) и есть более новая **major или minor** версия, которую пользователь не скрывал (`update_dismissed_version`), эмитится событие `update:available` с `UpdateInfo`. Фронтенд показывает закрываемый баннер сверху (`UpdateBanner.vue` в `AppShell`); «Обновить» ведёт в Настройки → О программе (`#updates`) и автоматически запускает проверку, «✕» сохраняет `update_dismissed_version` (не показываем повторно после перезапуска). `PendingUpdate()` — backfill на случай, если событие пришло до подписки слушателя.

**Определение значимости:** `versionBump(current, latest)` через `semver.Major`/`semver.MajorMinor` → `major`/`minor`/`patch`/`none`. Пассивно показываем только `major`/`minor`; `patch` — тихо (доступен вручную в панели). Поле `Severity` добавлено в `UpdateInfo`.

**Почему только при запуске:** просто и предсказуемо, без таймеров и лишних запросов к GitHub API. Периодическую проверку можно добавить позже.

## Риски и компромиссы

- **[Риск] macOS: замена .app-бандла ломает кодовую подпись** — Gatekeeper проверяет подпись нового бандла. Если архив содержит неподписанный `.app`, macOS может заблокировать запуск. **Смягчение**: CI-сборка под macOS подписывает `.app` ad-hoc подписью (`codesign --force --deep --sign -`), что удовлетворяет Gatekeeper для ненотаризованных приложений. В документации указать, что может потребоваться правый клик → Открыть при первом запуске после обновления.
- **[Риск] Windows: антивирус блокирует PowerShell-скрипт** — создание и запуск скрипта, заменяющего `.exe`, может триггерить эвристики. **Смягчение**: использовать только стандартные командлеты (`Copy-Item`, `Start-Process`, `Remove-Item`), без обфускации. При блокировке скрипт просто не срабатывает, оригинальный `.exe` остаётся нетронутым.
- **[Риск] Linux: путь к бинарнику неизвестен заранее** — приложение может быть установлено куда угодно (`/usr/local/bin`, `~/.local/bin`, свой путь). **Смягчение**: использовать `os.Executable()` для определения пути запущенного бинарника во время выполнения.
- **[Компромисс] Без автоматических проверок** — сохраняет фичу простой и подконтрольной пользователю. Фоновые проверки можно добавить позже как опциональную настройку.
- **[Компромисс] Полный архив каждый раз** — релизный архив весит ~50-100 МБ. Приемлемо для целевой аудитории на широкополосном интернете. Дельта-обновления добавили бы значительную сложность при минимальном выигрыше.
